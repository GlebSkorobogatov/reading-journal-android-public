## 1. Миссия и границы

Создаём личный офлайн Android-дневник чтения на Kotlin + Jetpack Compose. Целевое устройство для ручной приёмки — Samsung Galaxy A55. Продукт учитывает чтение, страницы, циклы, записи, аналитику и достижения. Не является электронной читалкой. Нет аккаунта, обязательного интернета, сервера, облачной синхронизации, телеметрии, сетевого каталога книг или публичной публикации. Не добавлять такие функции без нового утверждённого требования.

Воспроизводи утверждённый дизайн, а не предлагай альтернативный дизайн. Качество, целостность данных и предсказуемость важнее скорости и количества реализованных функций. Не оптимизируй объём путём удаления обязательного поведения.

## 3. Разрешение на работу и предварительная проверка

Один запрос — один явно разрешённый TASK-ID из IMPLEMENTATION_PLAN (или отдельный согласованный docs/repair scope). Ни утверждение документа, ни открытие PR, ни успешный CI, ни молчание владельца не разрешают следующий этап. Не запускать код до DOC, REPO и отдельного разрешения UI-01. При запросе только на анализ, аудит, review или планирование не менять файлы и remote.

Перед изменениями:

1. Проверить рабочую директорию и настоящий репозиторий, `git status --short --branch`, текущий SHA, принятую базу, доступные ветки и контекст PR. Не переключаться с чужих незакоммиченных изменений и не стирать их. Если база не совпадает с заданием или рабочее дерево содержит конфликтующие изменения — остановиться и сообщить.
2. Прочитать карточку текущего ID, связанные PRD ID/AC, применимые секции архитектуры, дизайна и тестов; проверить актуальные инструкции AGENTS.md в затрагиваемых каталогах. Вложенные инструкции не должны тайно менять договор проекта. При конфликте сообщить владельцу.
3. Зафиксировать цель, границы разрешённых файлов/пакетов, запреты, ожидаемые состояния, план проверок, базовый SHA и зависимости. Уточнить только существенные неизвестные. При ясном утверждённом задании выполнять его без повторного запроса согласия на каждую строку.
4. Если задача слишком широка для одного прохода, предложить согласованные части ID-a/ID-b с сохранением исходного gate; не брать соседний этап ради удобства.

## 4. Жёсткая последовательность разработки

`DOC → REPO → UI-01 → UI-02 → UI-03 → UI-04…14 → UI-READY → F-01…15 → FUNCTIONAL-READY → QA-01 → QA-02 → REL-01 / PERSONAL-READY`.

- DOC: семь основных документов, действующие решения, ADR и реестр референсов согласованы; код не создаётся. REPO: отдельное разрешение на приватный репозиторий, первый docs-only commit и проверка приватности/версий. Не смешивать репозитории разных проектов.
- UI-01 — только дизайн-система, темы, общие компоненты, навигационный каркас, минимальная собираемая основа и CI. UI-02 — только Главная, UI-03 — только Библиотека, оба на демонстрационных данных. Не объединять эти задания, не выполнять их параллельно.
- UI-04…14 — остальные согласованные интерфейсы, каждое с отдельной приёмкой. UI-фаза использует локальные детерминированные fixtures, контракты и UI-state; не подключать настоящую Room, реальный таймер, начисление XP, реальный импорт/экспорт или рабочую бизнес-логику. Можно только изучить техническую осуществимость и создать минимальную инфраструктуру, разрешённую карточкой.
- После UI-READY получить отдельное разрешение на F-фазу. В F-01…15 подключать настоящие данные постепенно через уже согласованные контракты; не переписывать принятые экраны. Неподключённая функция явно незавершена, не подменять её реальные результаты mock-данными. Не записывать demo в пользовательскую библиотеку; убрать деморежим из обычной сборки к F-15.
- После каждого ID: отчёт, тесты, обязательная A55-проверка, явное утверждение, отдельное разрешение merge и зафиксированная принятая база. Для следующего ID — отдельное разрешение. UI-READY, FUNCTIONAL-READY и PERSONAL-READY закрывать по TEST_PLAN, а не по процентам прогресса.

## 5. Правила Git, GitHub и изменения файлов

- Одна разрешённая задача — одна отдельная ветка `codex/<id>-<slug>` от указанного принятого SHA, небольшой Draft PR. Название и базу сверить с текущим заданием. Утверждённая база может быть веткой принятого предыдущего PR, если владелец явно это указал. Не предполагать, что `main` содержит последние принятые изменения.
- Использовать только разрешённые репозиторий, ветку и scope. Ветка/коммит/push/Draft PR допустимы в объёме явного задания; если удалённое действие не разрешено или недоступно — описать локальный результат, не имитировать публикацию.
- Не делать самостоятельно merge (включая squash/rebase merge), force-push, reset --hard, массовое удаление, переписывание истории, изменение защиты веток, приватности или прав. Не откатывать чужие изменения. Любые такие действия требуют отдельного разрешения и проверки последствий; не предлагать разрушительный способ как стандартный.
- Не коммитить секреты, ключи подписи, токены, личную библиотеку, реальные заметки, обложки, экспортные копии, локальные БД, машинно-зависимые настройки и кэши. Не отправлять личные данные во внешние сервисы/логи. Проверять diff и staged-файлы. Использовать синтетические fixtures и безопасные имена.
- Избегать массовых рефакторингов, форматирования посторонних файлов, незапрошенных зависимостей и обновлений стека. Не исправлять несвязанные дефекты молча: сообщить и предложить отдельный repair scope. Не удалять или подменять утверждённые документы/референсы. Новые ADR, отчёты и изменение README — только в рамках задачи и фактического состояния.

## 6. Инженерные правила

- Один модуль `:app`, логическое разделение UI/application/domain/data/platform по ARCHITECTURE. UDF/StateFlow/ViewModel, immutable UI-state, однонаправленные события, чистые функции расчёта, явные репозитории и внедрение зависимостей. UI не выполняет SQL, файловые операции или расчёты XP. Не вводить новые Gradle-модули, фреймворки DI/навигации или сетевые библиотеки без обоснованного согласованного решения.
- Kotlin: ясные имена, небольшие функции, типобезопасные модели состояний, явная обработка ошибок и отмены coroutines. Не подавлять исключения, не использовать `!!` как обход валидации, не подменять неизвестное значение нулём. Избегать блокировки main thread, бесконтрольных coroutine scopes, утечек и неоправданных абстракций. Приоритет существующих проверенных соглашений проекта.
- Room — источник сохранённых фактов и резервируемых настроек в функциональной фазе; производные величины пересчитываются. Транзакции, стабильные ID, ограничения связей, безопасные миграции, идемпотентные операции. Не применять destructive migration, удаление данных или сброс БД как способ исправить проблему. Тестировать старую и новую схемы. Изображения хранятся локально отдельно от БД.
- Не выбирать SDK/версии инструментов наугад. UI-01 должен обосновать и проверить Gradle/JDK/AGP/Kotlin/Compose/SDK, совместимость и команды CI. minSdk 26 — кандидат архитектуры, не доказанная совместимость. Фоновая служба, формат Markdown и подпись — технические задачи соответствующих ID. Проверять официальные документы платформы и фактические ограничения среды; фиксировать ADR. Не добавлять лишние разрешения или зависимость от сети во время использования приложения.

## 7. Неприкосновенность дизайна

UI_DESIGN_SPEC — обязательный контракт, не референс «по настроению». Использовать единые токены цветов, типографики, размеров, скруглений, состояний и анимаций. Не вводить собственные HEX, динамические цвета или иные шрифты в обход системы. Lora/Manrope с кириллицей офлайн; проверить лицензии и реальное отображение. Не копировать бренд Claude. Не публиковать файлы шрифтов пользователю.

Тёплая светлая и графитовая тёмная темы, системный режим; три главных вкладки без плавающей подложки, активная линия, настройки сверху. Внутри книги — три согласованные вкладки и правила посещения/прокрутки. Упрощения влияют только на состав функций. Не возвращать радар, расширенный редактор, секретные награды и другие отменённые элементы даже в демонстрации.

Проверять обе темы, системный fontScale, длинные русские строки, маленькое окно/поворот, safe insets, системные жесты, контраст, доступные touch targets, semantics и reduced motion. Использовать утверждённые компоненты и Preview на основных состояниях. Не маскировать обрезку текста уменьшением шрифта против утверждённой шкалы. Скриншоты/Preview — доказательства конкретной сборки; новые эталоны утверждает владелец на A55. Не объявлять HTML/условную иллюстрацию реальным Android-макетом.

## 8. Критические продуктовые инварианты

Это контрольный минимум, а не замена PRD, ARCHITECTURE и TEST_PLAN. Применять только к разрешённому этапу.

- Один незавершённый цикл на книгу, один активный таймер. Последняя страница не завершает цикл автоматически. Исторические прочтения не награждать. А4: заметки/цитаты — книга, отзывы/оценки — цикл.
- Время — достоверные активные секунды, без пауз. Таймер: монотонное время отдельно от календарных привязок; не угадывать время после сбоя. Ручной сеанс: дата + длительность. Проверять дубль и суточные ограничения.
- Один диапазон на событие или неизвестные страницы; общий объём включает повторы, уникальный — объединение диапазонов. Закладка независима. А1: добровольная точная разбивка по дням с проверкой суммы; если неизвестна — общий объём без вымышленной разбивки и нулей.
- TZ-01: закрепить зону при первом сохранённом факте с конкретным днём учёта; не от создания книги/тега/технической даты заметки. Временный запрет смены при активном или приостановленном таймере; удаление фактов не разблокирует. Восстановление сохраняет состояние зоны.
- XP: 1 за полную накопленную минуту, +100 за действительное завершение один раз на цикл (А2 — дата подтверждения, не редактируемая дата книги), четыре источника. Серия ≥300 активных секунд/день. А3: 3×5 ступеней, 1575 XP; личные достижения однократные, 0–600 XP. Пересчёт детерминирован, без дублей; обычный пропуск дня не отменяет исторический рекорд.
- Один ручной восстанавливаемый Markdown без обложек, пароля и автонапоминаний; предупреждение, проверка файла до изменения БД, подтверждение полной атомарной замены, заглушки. Не добавлять ZIP, папки или выборочный импорт. Ошибка/отмена сохраняет действующие данные; не перезаписывать старые успешные копии.

## 9. Проверки, CI и доказательства

TEST_PLAN задаёт обязательные проверки по ID, AC-01–27, R-01–42, NFR и матрице покрытия. Считать тест доказательством только при фактическом выполнении. Сначала изучить существующие команды README, Gradle wrapper и CI; до UI-01 команд сборки может не быть. После появления проекта выполнить применимые build, lint, JVM/Room/Compose/Android тесты, `git diff --check` и релевантную регрессию. Не придумывать команды/задачи Gradle, число тестов, существование APK, статус CI или ссылки. Если тесты/CI недоступны, явно указать причину и какой gate блокируется.

- Проверять ожидаемое поведение и отрицательные сценарии; не только happy path. Для изменений расчётов добавлять/обновлять тесты с утверждёнными оракулами, фиксированными часами и датами, границами полуночи/DST, дробными остатками и неизвестностью данных. Тесты на отказ/rollback использовать на fixtures, не на пользовательской библиотеке.
- Не удалять, не отключать, не ослаблять assertions и не заменять ожидаемые значения на фактические ради зелёного CI. Не скрывать warnings, ошибки, flaky tests и skips. Если существующая ошибка не относится к задаче — фиксировать baseline и объяснить, не выдавать FAIL за PASS.
- Результаты: PASS/FAIL/NOT RUN/N/A/BLOCKED с объяснениями; команда, среда, SHA, фактический вывод/ссылка и число passed/failed/skipped, если известно. N/A только с обоснованием неприменимости. При изменении кода после проверки повторить релевантные проверки на новом SHA.
- Автотесты не заменяют ручную проверку A55. Для задач UI — обе темы, навигация, читаемость/масштаб и скриншоты; для функциональных — реальное поведение, фон/блокировка, данные, ошибки и сохранность согласно карточке. Указать APK: вариант, versionName/code, SHA-256, источник; дать короткие шаги пользователю. Не заявлять, что смартфон проверен, если владелец ещё не выполнил шаги. Эмулятор — отдельный вид проверки.
- Блокеры и Major по TEST_PLAN запрещают закрыть gate: потеря данных, ошибочные время/страницы/XP, фальшивый успех, crash основного маршрута, утечка, нарушение обязательного UX/дизайна, обязательный FAIL или NOT RUN. Minor можно отложить только по явному решению владельца. Если лимит среды мешает завершить проверку, остановиться с частичным отчётом; не переходить дальше.

```text
Ручная A55-проверка: шаги, ожидаемое; кто и когда проверил, если уже сделано
Дефекты, ограничения, отклонения, NOT RUN/N/A: ...
Безопасность данных / миграции / откат (если применимо): ...
Следующее необходимое действие владельца: ...
Merge и следующий TASK-ID: не разрешены, если нет отдельного согласия
```

Отдельно отмечать предположения и технические решения, принятые в пределах делегирования. Не заявлять полную готовность при частичной реализации. Утверждение отчёта не подменяет подтверждение владельцем APK; запись о факте приёмки должна ссылаться на действительное подтверждение. Не заполнять её за владельца.

## 11. Завершение и поддержание инструкций

По окончании одного задания прекратить изменение проекта. Ожидать ручную приёмку и отдельное разрешение на merge/следующую задачу. Если обнаружены существенные несогласованности, показать их, не менять молча. При новом утверждённом продуктовом решении обновлять только явно разрешённые документы, журнал/ADR и связанные тесты, сохраняя предыдущую версию/историю. Не менять AGENTS.md самостоятельно ради обхода ограничений и не создавать вложенные override-файлы для их отмены.

Конкретные команды сборки и реальная структура файлов появляются после UI-01; их фактическое состояние фиксировать в README и отчётах, не дублировать в AGENTS.md. Инструкции должны оставаться компактными и применимыми к любой стадии проекта.
