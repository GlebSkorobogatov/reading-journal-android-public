## 2. Общий контракт каждого задания Codex

Каждая карточка §4 задаёт цель, ссылки на полные требования, разрешённый scope, запреты, автоматические тесты, A55-проверку, ожидаемый результат. Это план задач, **не готовые промпты на запуск**. Перед исполнением формируется один самостоятельный промпт на основе актуального состояния принятой ветки, с перечислением затрагиваемых файлов/допустимых пакетов, точным base SHA, версией документов и критериями ниже. Если объём оказывается слишком большим, разделить на подпункты `ID-a`, `ID-b` только после согласия; исходный gate сохраняется, следующая задача не начинается до приёмки всех частей. Не сливать несколько задач ради лимитов или скорости.

**Порядок:** выбрать единственный ID → подтвердить цель/base → создать отдельную ветку `codex/<id>-<slug>` от принятой базы → малый Draft PR → CI и отчёт → APK/ручная проверка → исправления в пределах задачи (или отдельный корректирующий PR) → явное утверждение → отдельное разрешение объединить/зафиксировать принятую базу → следующий ID. Никаких самостоятельных merge/force-push. Повторно проверять принятую базу и конфликты. Имена веток — соглашение проекта, не существующие ветки. Не считать отсутствие ответа согласием.

**Универсальные критерии:**

1. Scope соответствует карточке и актуальным ID; затронутые файлы объяснены. Запрещённые функции не реализованы. Новые технические решения/ограничения отражены в ADR и не меняют продукт без согласия.
2. После появления Android-проекта: воспроизводимая debug-сборка, lint, релевантные JVM/инструментальные/Compose тесты, отсутствие необъяснённых регрессий. Конкретные Gradle-команды и CI workflow зависят от UI-01 и TEST_PLAN. Не придумывать результаты и не требовать несуществующие команды до проекта. Указать PASS/FAIL/NOT RUN с причиной, числом тестов и SHA. Критические FAIL или обязательные NOT RUN блокируют приёмку соответствующего gate.
3. A55 — установленная APK с проверяемой версией и источником; для UI проверить обе темы, масштаб, русские надписи, доступность и эталонные скриншоты; для функциональных задач — фактические данные и сохранность. Проверки, которые не применимы к задаче, помечать N/A с причиной. Отчёт Codex не подтверждает ручную проверку, которую владелец ещё не выполнил.
4. Любая ошибка или частичная готовность явно указаны. Demo и production sources разделены; неполная функция не показывает ложный успех. Не записывать demo-книги в рабочую базу. До F-15 остальные ещё не подключённые части явно обозначаются незавершёнными, не смешивать значения mock с реальными.
5. Отчёт: ID, цель/base/head SHA, branch/PR, список файлов и изменений, покрытие PRD/AC, команды+результаты, артефакт APK/ссылка, screenshots/Preview (где применимо), инструкция A55, ограничения/отклонения, риски, действия по откату, статус «ожидает приёмки». При изменении БД — миграция и стратегия сохранения пользовательских данных. Никаких секретов в отчётах.
6. Приёмка владельцем обязательна; исправления повторно проходят релевантные проверки. Gate закрывается только после результата проверки, а не по истечению срока. Принятый baseline и документированное разрешение на следующий шаг — часть контроля.

### UI-01 — Дизайн-система и навигационный каркас

**Цель и требования:** SCOPE-03,07; NAV-01–06,12; NFR-01,03,04,06.

**Разрешено (scope):** Создать минимальный :app Kotlin/Compose; выбрать совместимый набор SDK/Gradle/JDK и проверяемых зависимостей в рамках ARCHITECTURE §2, зафиксировать версии и лицензии. Реализовать утверждённые токены UI_DESIGN_SPEC §§1–4, темы, typography, компоненты, Preview, корневую навигацию и пустые демонстрационные маршруты. Минимальные state/event contracts, явная demo-среда. Настроить CI сборки и доступных тестов.

**Запрещено / вне scope:** Никаких полноценных Главной/Библиотеки/Достижений, Room, таймера, XP, реального хранения книг, экспорта. Не изменять токены; не подключать сеть или dynamic colors взамен палитры.

**Автоматическая проверка:** Сборка debug, lint, тесты маршрутов/состояния тем и базовых компонентов; Preview обеих тем, русский длинный текст, системные insets. Screenshot-проверки, если инфраструктура воспроизводима; иначе обосновать отсутствие.

**Ручная проверка A55:** Установить APK на A55; холодный старт, три вкладки, шестерёнка, back, светлая/тёмная/системная темы, 100% и увеличенный шрифт, поворот, жестовая/кнопочная навигация где доступна. Снять эталоны компонентов.

**Готовность и отчёт:** APK + проверяемый CI + каталог компонентов + скриншоты; явная приёмка UI-01 владельцем. Обязателен отчёт по §2, явная приёмка и согласование следующего задания.


### UI-02 — Главная — только демонстрационный интерфейс

**Цель и требования:** NAV-01–06; TIME-01–07,16; ANALYTICS-02–32; XP-05–07,24–25,32; NFR-03,04,06.

**Разрешено (scope):** Только Главная: все активные книги вертикально, закреплённые первыми; карточки прогресса, визуальные состояния одного таймера/мини-панели; далее иллюстрированная XP-карточка, три фиксированные метрики, шесть периодов и пять секций аккордеона, открыта не более одной. Внутри секций демонстрационные столбцы, годовой heatmap, сравнение, скорость/прогноз и шесть рекордов. Подробности дня/графика — временные точки перехода до UI-09. Фикстуры пусто/одна/много/неполнота/ожидание/пауза.

**Запрещено / вне scope:** Не реализовывать библиотеку, реальные часы, уведомления, XP, статистику, БД; не добавлять радар, месячный календарь, настройку метрик, сетевые данные. Не выдавать mock за настоящий таймер.

**Автоматическая проверка:** Compose UI tests порядка элементов, переключения периода, единственного раскрытого блока, навигации/мини-таймера и неизвестности; демо-тесты без настоящих вычислений; screenshot fixtures.

**Ручная проверка A55:** A55 в обеих темах: вся вертикальная лента, прокрутка, несколько книг, XP-иллюстрация, все блоки, мини-таймер не перекрывает навигацию, крупный шрифт и пусто.

**Готовность и отчёт:** Отдельный APK/PR, утверждённые скриншоты Главной; UI-02 принят явно до начала UI-03. Обязателен отчёт по §2, явная приёмка и согласование следующего задания.

## 6. Правила постепенного переключения demo → реальные данные

- UI-01–14: только in-memory/demo fixtures, отдельный режим тестовой сборки и Preview; типы UiState/UiEvent и навигация соответствуют архитектуре. Фикстуры покрывают 0, неизвестность, минимум, PENDING, historical, длинные строки, пусто, ошибки, loading только где обоснован.
- F-01: Room и интерфейсы репозиториев, без ложного подключения. F-02–14 заменяют источник конкретной подсистемы; запрещено смешивать реальные и вымышленные итоговые цифры. Если зависимый показатель ещё не подключён, отображать честное состояние недоступности в промежуточной тестовой сборке и фиксировать в отчёте. Не выдавать промежуточный экран за финальный. Не переопределять утверждённое конечное поведение.
- Все изменения общего UI при интеграции требуют сравнения с эталоном и отдельной приёмки, даже если архитектурно разумны. В F-15 удалить demo-подключение из обычной пользовательской сборки, сохранить фикстуры только в тестах/Preview. Проверить, что чистая установка не заселена демонстрационными данными.
- Не предлагать владельцу начать вести единственную реальную историю в тестовых промежуточных сборках без предупреждения о незавершённых миграциях. Не использовать реальные личные записи в CI, PR, отчётах или скриншотах без разрешения. Не удалять тестовую базу на устройстве как способ устранения миграционного дефекта без явного согласия.
